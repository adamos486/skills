Why · Shape · Build · Done

Why we're doing this

Users get every notification we send, with no way to turn any of them off. Support gets about four complaints a week about it. We want a settings page where a user can toggle each of our five notification types on or off, and we want to respect those toggles when sending.

This is for our existing web app — Next.js front end, Django backend, Postgres.

The shape we landed on

We talked about a generic preferences framework that could hold any key/value setting for any future feature, with a schema registry and per-key validators. We decided against solving that now — we have five booleans.

Instead: one notification_preferences table, one row per user, five boolean columns. A NotificationPreferences model, and a check in the send path.

What we'll build

  1. Migration adding notification_preferences, defaulting every column to true so existing users keep current behavior.
  2. Django model plus a get_or_create accessor so users predating the migration get a row on first read.
  3. GET and PATCH /api/notification-preferences, scoped to the requesting user.
  4. A settings page with five toggles, saving on change.
  5. A guard in the notification send path that skips a send when the matching toggle is off.

How we'll know it works

  • A user turning off "product updates" stops receiving product updates and keeps receiving the other four types.
  • A user who existed before the migration has all five on by default.
  • One user's preferences never affect another user's sends.
